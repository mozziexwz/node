# 受信中转恢复与证书维护

本页描述受信恢复协议与审核要点；该能力最早随 v0.2.4 配套镜像提供，v0.2.3 不具备。控制面支持官方 Debian 12/13 单机 Compose 部署，节点需使用支持本恢复协议的 keep_last Agent；具体系统范围见[平台支持](platform-support.md)。公开安装菜单不提供控制面恢复入口；没有经过审核的专用本机运维入口时，应保留现场而不是尝试普通升级或重注册。发布不等于现有控制面或节点已升级，也不得把源码单测当作现场不断流验收。

## 恢复前提

灾难恢复仍使管理令牌失效、保留端口/目标/撤销关联、保持维护并关闭经营。先停止或可靠隔离旧控制面，保留旧磁盘和外部账本。相同域名不是新控制面获得授权的依据。执行器、客户 DD 和独立客户 VPS 不由本流程重新注册或重放任务。

必须有原节点 root 本机访问权，原 Agent/GOST 仍运行且本机状态完整。凭据重载不重启 Agent/GOST；节点或进程本身已经重启时，不能恢复过去的 TCP 会话。旧无 v2 状态、原记录缺失、未知拓扑或损坏数据会保留现场拒绝，不设超时强制接管。

## 两端受保护操作

受信恢复专用工具仅限控制面本机 Linux root 真终端交互使用，不接受普通命令行参数或定时器调用。每次都先核对原 `.env`、本机固定镜像、唯一 server / 数据库，以及 server 实际 `MASTER_KEY`、`PUBLIC_URL` 与数据库配置；不会拉镜像或停止、重启服务。密钥核对只通过匿名管道传给禁用容器日志的隔离工具，不打印环境内容。此流程不是 `msboost` 公共管理菜单的一部分；以下操作顺序是恢复协议说明，不是可直接粘贴执行的公共入口。

控制面也需先创建 `/root/msboost-recovery`，权限 0700。输入必须是 root 所有的普通 0600 文件、无额外硬链接和符号链接；每次输出都选该私有目录中**尚不存在**的新文件。文件及各级目录不可由其他用户写入，编辑器保存后也要保持这些条件。不要把输入和输出设为同一文件。

| 操作 | 输入文件内容 | 新输出文件内容 |
| --- | --- | --- |
| `inspect` | 节点原始 snapshot，或包含 `snapshot` 的恢复请求 | 可直接审核编辑的 prepare 请求模板，附 `review` |
| `prepare` | 上一步模板，仅修改精确决策与确认 | 可直接交给原节点 `adopt` 的完整私有计划 |
| `status` | **不需要输入文件** | `controlEpoch`、`recoveryRequired`、`maintenance`、节点计划与确认状态 |
| `finalize` | 仅含精确 `confirmation` 的对象 | 完成核对的消息，不开放维护/经营开关 |
| `tls-inspect` | `{"ruleId":"准确规则ID"}` | TLS **报告**，不是可直接提交的轮换请求 |
| `tls-rotate` | 仅含 `ruleId`、`fingerprint`、`confirmation` | 新 TLS 报告；提交不代表节点已应用 |

每个操作还需在终端单独输入 `RELAY_RECOVERY <操作名>`；这不能代替 JSON 内要求的旧站隔离、财务或 TLS 风险确认。所有结果保存后需在本机私有编辑器查看，命令不会把 JSON 显示在终端。此入口也不会清除整站 `backup-pause` 门禁；若该门禁残留，必须先依整站备份文档使用**原 token**处理，不能用中转恢复代替解锁。

1. 在每台原节点 root 终端创建私有结果目录，使用**已安装的新版** Agent 导出快照：

   ```bash
   install -d -m 0700 /root/msboost-recovery
   /usr/local/bin/msboost-agent --capability relay-recovery \
     --state-dir /var/lib/msboost-relay --recovery-action snapshot \
     --recovery-file /root/msboost-recovery/node-snapshot.json
   ```

   这会持久化本机恢复冻结，保留原连接。快照包含原控制身份、每条命令/已应用配置的代次和哈希、实际进程观察、撤销记录与未确认计量，不含 TLS 私钥或管理令牌。原目录 0700、Unix socket 0600，服务端验证调用者 Linux `SO_PEERCRED` 为 root；不能从网页或远程同步调用这个本机授权入口。

2. 通过可信 SSH/SFTP 把快照传到新控制面 root 的 0700 目录，文件保持 0600。使用受信专用工具的 `inspect` 操作，输入快照路径和**不存在的新输出路径**，例如 `prepare-request-01.json`。此步接受节点原始快照，无须手工包一层 JSON；输出带 `snapshot`、`fingerprint`、`decisions`、`confirmation` 和 `review` 差异表的私有请求模板。此步只读控制面；默认每条 `decisions[].action` 为 `hold`，`confirmation` 为空。

3. 在私有请求文件中逐条审核，只改决策与确认：

   - `adopt`：仅完整命令与数据库相同、原配置实际已应用时可用；已确认停止的墓碑继续保持停止，不会复活。
   - `stop`：针对精确原记录生成更高代次的明确 revoke；只停止指定规则，必须等实际退出后的 ACK，不能把提交当作停止完成。
   - `hold`：保留当前配置并继续冻结；有任一 hold 就不能完成该节点或整站恢复。

   不改快照、ID 或指纹来“消除差异”；`review` 仅供显示，保留原样即可，它不是授权证据。填写 `confirmation` 为 `OLD_CONTROL_ISOLATED <该快照的 recoveryId>`，确认旧站确已隔离。再用受信专用工具的 `prepare` 操作，以编辑后的 `prepare-request-01.json` 为输入，保存到不同的新私有计划文件，例如 `trusted-plan-01.json`。计划含新管理令牌及必要的 TLS 配置，绝不能上传公开仓库、工单、聊天或容器日志。工具不自动重试写操作。

4. 把计划私密传回对应原节点，root 执行：

   ```bash
   /usr/local/bin/msboost-agent --capability relay-recovery \
     --state-dir /var/lib/msboost-relay --recovery-action adopt \
     --recovery-file /root/msboost-recovery/trusted-plan.json
   ```

   Agent 在同一持久状态更新中写入新凭据、控制代次和精确决策；同哈希接管不重启 GOST。相同计划可幂等重试，修改后的同一计划、旧代次、缺项或当前记录变化会拒绝。旧凭据正在进行的请求，其响应不能跨过这次切换生效。新控制面先只收匹配 ACK 并返回空命令，不自动执行恢复库中的停用或重新部署。

5. 用受信专用工具的 `status` 操作查看每台节点是否全部决定、是否已有匹配确认。hold 后继续处理时，重新取得该节点当前受保护快照，再 inspect/prepare 下一份递增计划。数据库存在而节点快照缺失的记录不自动认定停止；必须保留现场核实原节点/安装实例。

6. 核对外部支付和历史用量，审核/启用拟继续运行的节点与路线；此时全站仍处于恢复冻结，不能创建新业务。所有保留运行配置必须与当前拓扑、速率和权益一致；已到期、超额或拟停用的规则应先通过明确 stop 处置，不以接管掩盖经营策略差异。

   在私有 JSON 文件中填写 `{"confirmation":"OLD_CONTROL_ISOLATED_AND_FINANCES_REVIEWED <status中的controlEpoch>"}`，再用受信专用工具的 `finalize` 操作。同一数据库事务会重验全部原始目录、计划/令牌/代次、每条 ACK、原拓扑及 90 秒内确认，任何孤立、缺失、重复、坏记录或已重置身份都会拒绝。通过后仅解除中转恢复冻结；维护模式、支付和经营开关仍需另行审核开放。

## 结果不明与财务边界

受信专用工具的输出和 stderr 都写 root 私有文件。原子发布不覆盖已有目标，失败保留 `.msboost-relay-recovery.*` 目录。先看 status/原现场，使用**原请求**核对；不要生成新令牌、删除记录或反复准备不同计划来试错。新备份恢复产生新的控制代次后，旧计划不能继续使用。

本流程不修改余额、权益、订单或历史账本，也不会确认尚未入账的流量。Agent 正常离线期间保留的样本在完成恢复后按原周期协议补报；已在旧库确认、随后从 Agent 清除的历史用量可能不可重建，`historyIncomplete` 始终明确为真。要获得更强灾备恢复点，需独立数据库日志/外部账本；不能声称旧快照恢复后绝不丢账。

`accountingDegraded` 不会被恢复或删除按钮清除，也不能接管为继续运行。为避免无法退役的死锁，唯一受保护退出是：先在根恢复计划中把该节点的**全部非空命令**明确设为 `stop`，收到每条精确、新鲜的 `revoke / stopped` ACK，再由 root 完成上述旧站隔离与外部财务核对确认。`finalize` 会保存绑定原节点、实例、控制代次、计划、命令/历史和快照摘要的终态财务核对证据，仍保留降级标记和全部计量资料；`pause`、运行配置、`hold`、空库存或未知停止均不能使用这个出口。

随后等规则完成撤销归档，删除所有引用该节点的线路，再执行后台节点删除。删除会重新验证完整停止证明和未变化的根核对证据，将不可再注册的旧节点身份归档，**不删除**原命令、撤销历史、目录或账务。只有这些已证明的终态身份在未来恢复时可以不再索取现场 ACK；缺归档、坏证据、库存丢失或旧身份重现仍会拒绝。新节点必须使用全新身份，不能把这个终态审计当成恢复旧节点经营或清理旧账的许可。

## 显式 TLS 维护

普通 v2 重连不轮换证书。受信专用工具的 `tls-inspect` 操作接收 `{"ruleId":"准确规则ID"}` 的私有文件，取得 `ruleId`、`fingerprint`、`tlsExpiresAt`、`segments`、`message` 报告；其中指纹绑定当前配置，不能自行生成。

开启维护并确认所有受影响节点正常后，**另建** root 0600 私有请求文件，只含下面三个字段。把报告中的真实 `ruleId` 和完整 `fingerprint` 原样填入，并替换确认字符串中的规则 ID；尖括号是占位符，不应保留：

```json
{
  "ruleId": "<报告中的真实规则ID>",
  "fingerprint": "<报告中的完整64位指纹>",
  "confirmation": "ROTATE_TLS_INTERRUPTS_RULE <同一个真实规则ID>"
}
```

不要直接把 `tls-inspect` 整份报告提交给 `tls-rotate`：`tlsExpiresAt`、`segments`、`message` 是输出字段，严格解析会拒绝它们。受信专用工具的 `tls-rotate` 操作输入这份三字段请求，输出使用另一不存在的新文件，并在终端确认 `RELAY_RECOVERY tls-rotate`。全站停站备份门禁、活动/未知任务、网页备份、恢复冲突或不满足完整 v2 确认的链路仍会阻止轮换；旧链路风险确认不会绕过这些条件。

轮换只修改所选完整规则的新证书、上游固定信任和显式配置代次；不会关闭证书/主机名验证。真实配置变化可能断开该规则的原连接，需维护窗口；其它规则不会被重新部署。提交不等于已应用，必须等待每一段的新 ACK。正常心跳和流量观察不会使稳定配置指纹失效；配置、代次或拓扑变化则必须重新检查。

## 长期状态与迁移

配置和撤销记录最多 4096 条，计量待报有独立有界容量。达到上限时拒绝新配置并告警/进入账务降级，不通过自动删除墓碑、重置计量或清空状态换空间。保留私密完整备份并安排受控维护：先对旧实例全部明确撤销并收到停止证明，再退役旧身份、使用全新受管节点身份部署；不复用旧实例 ID，也不把旧数据库回放当成回滚。在线墓碑压缩、无限期历史保留和 Agent 升级保连接不是本流程的承诺。

新 systemd 的 id-mapped 状态目录可能改变宿主机 UID 映射；无论控制面运行在 Debian 12 或 13，还是节点使用受支持的 Agent 系统，都不能为了跨平台适配而放宽 socket 的调用者/服务身份检查。
