# Relay v2：keep_last 契约与发布边界

全新 Relay 安装默认使用 `keep_last`。受控 30 分钟耐久达到既定基线，**但仍不是生产全场景“离线不断流”保证**。部署者应核对所用版本的 Release 制品、CI 结果和现场状态。

## 兼容与启用范围

全新 `--capability relay` 安装在未指定策略时使用 `keep_last`，通过独立 `/api/relay-agent/v2/sync` 同步。旧链仍可显式指定 `--offline-policy lease`，继续使用 `/api/relay-agent/sync` 的 v1 短租约。v0.2.4 的历史默认值是 lease；网站升级、版本号变化或控制面重启都不会自动切换已有节点。

已有活动 lease 服务迁移到 keep_last 必须逐台、逐条完整线路安排维护，并显式传 `--offline-policy keep_last --acknowledge-relay-restart`。升级 Agent 会结束其子进程和原 TCP 连接，不属于管理失联不断流的保证范围。建议优先在全新 Debian 12 节点安装验证，再决定是否迁移旧节点；缺少重启确认时安装器必须在停止原服务前拒绝。

已有 v2 本地状态时拒绝静默降级到 lease；服务端也拒绝已登记 v2 节点用旧同步协议修改状态。未知协议、HTTP 401/403、DNS/TLS/HTTP 故障不会成为 v2 停止指令。

## 控制消息

- 首次两阶段握手先持久化 `controlEpoch`，只返回空命令；客户端回显代次后才生成配置命令。初始回包丢失可以重试。
- 请求绑定 Agent、进程实例、单调请求序号、随机请求 ID、已见目录 revision。回复必须匹配请求及已信任的代次；普通面板重启不改变代次。
- `upsert`、`pause`、`revoke` 是明确持久化命令。每条命令有不可变 ID、全局唯一规则实例 ID 和递增 generation。每次最多 32 条，遗漏永远不是删除。
- revision 是目录水位，不代表每条指令都已经送达。运行与停止仍以匹配命令 ID / generation / hash 的 ACK 为准；旧状态请求不能覆盖较新状态。
- 旧库、未知/领先实例状态、已退役 Agent 进程重新出现或控制代次变化进入 `recovery_required`。不能凭相同域名自动接管。

## 运行时与本地状态

- v2 没有管理失联到期关闭的定时器。保留最后已授权的监听、目标、ACL、速率与 TLS 校验；不在离线时自行扩大授权。
- runtimeHash 只包含真实影响 GOST 的参数，忽略租约、心跳、账务代次和统计。仅元数据改变不重启子进程。
- 验证整批候选、私密持久化意图、准备配置文件，再执行最小变更。无效候选和写盘失败不清空原有配置。
- 已通过验证的显式运行配置变更可能需要停止旧子进程并替换同端口监听；此后若真实 GOST 启动失败，只能重试已持久化候选，不能恢复已经结束的原 TCP 会话。这与仅管理失联或元数据更新不重启是不同边界。
- `relay-v2-state.json` 绑定服务地址、Agent 身份和控制代次；私有目录/文件检查、文件同步、原子替换和 Linux 父目录同步保护持久化。撤销记录不从缓存复活。
- Linux 在访问凭据、缓存与网络前获取安装目录排他 `flock`，拒绝同目录双实例；检查锁文件的所有者、权限、类型及链接。退出时等待全部子进程回收后才释放锁，不通过删除锁文件解锁。临时 Debian 12 跨进程状态锁、真实子进程回收与停止后拒绝新连接已执行通过，不仅是交叉编译。
- 暂停/撤销必须等待对应子进程实际退出、清理配置，并持久化结果后才能 ACK stopped。收到命令或调用 cancel 不算停止完成。
- 本机进程退出可独立重试；缓存重建不承诺保留原 TCP 连接。Linux 父进程死亡保护保留。
- 配置/墓碑目录当前上限 4096 条；达到上限拒绝新配置并等待维护，不自动删墓碑换取空间。

## 资源与多跳

v2 指令一旦持久化下发即保留资源，即使回复丢失。未获得相应停止证明前，超时不回收节点端口或解除统一旧目标锁。删除需要明确 revoke 终态；暂停不冒充撤销。

新入口仍等待下游首次部署确认；已运行入口不因下游管理心跳过期而被漏发或销毁。混合链路不宣称完整离线保留，任何一个 v1 段仍可能因租约到期关闭。普通同步不顺带自动轮换涉及 v2 的整链证书；显式证书维护与实际连接影响仍须验收。

## 流量与权益

- GOST 进程累计计数与账务 journal epoch 分离；只对指定计费入口记账，不对每一跳重复扣费。
- 节点保留最多 4096 条累计待报记录，每批最多 128 条轮转补报。只有当前请求明确匹配的样本 ACK 才可清除，ACK 检查点保存失败保留待报数据。
- 控制面事务提交成功后才返回流量 ACK。错误样本单独隔离，不回滚其他有效样本和控制通道。重复补报按累计游标去重。
- 历史授权保存在 `relay_v2_billing_grants`；旧权益样本仍计入原周期账本，但不扣新权益的 `TrafficUsed`。
- 采集区间明确在同一个 UTC 月且时间可信时按该月入账，不按恢复当天归集。跨月、跨账务切换边界或时钟异常的无法精确细分区间进入 `relay_v2_traffic_review` 和周期 `reviewBytes`，不伪造精确月份、不自动混扣新期。
- 管理员只读 `/api/admin/relay-accounting` 可以查看历史周期和待核对汇总；当前没有自动调账/批量扣款操作。
- 日志写失败或缓冲耗尽不会直接结束已有转发。标记 `accounting_degraded`；容量耗尽还累计可见缺口计数，冻结新配置。不是无限缓存或无条件零丢账承诺；降级需运维检查，不能当作验收成功。

离线期间不会另外按旧权益日期设置隐藏停用定时器。新的封禁、到期、额度耗尽决定在通信恢复后通过明确指令执行；这一控制延迟是 keep_last 的明确代价。

## 恢复安全

安全恢复保留当前 v2 资源与命令关联；完整灾难恢复对带 segments 的旧 v1 快照也保守保留，因为旧快照无法证明节点之后没有升级。

恢复仍撤销管理凭据、禁用线路并保持维护。保留规则实例、端口、目标锁、未确认撤销和账务数据，生成/标记恢复代次并冻结自动覆盖。**撤销管理令牌不等于停止旧转发。**

已实现受保护的本机恢复流程：节点 root 经 Unix socket 取得差异快照，控制面 root 在维护模式下逐条选择 adopt / stop / hold，并通过私有文件传回受信计划。运行配置完全匹配的 adopt 热切换管理凭据，不重启 GOST；stop 必须取得真实停止证明；hold 继续冻结。控制面取得精确命令 ACK 后，仍须 root 明确确认旧控制面隔离及财务核对，才能解除恢复冻结；维护与支付不自动开启。任何歧义、未知孤立命令或错代次均保守拒绝；账务降级不允许运行接管，仅在全体非空 revoke 均精确确认停止后，允许 root 留下绑定证据的财务复核审计并退役旧身份，绝不清除缺口或声称账务完整。详见 [恢复与证书维护](relay-recovery.md)。不得靠重新安装 Agent 冒充无损接管，也不得直接清空恢复标志绕过核对。

正常删除已终止 v2 节点会保存不可重新注册的退役身份及完整原目录/命令/历史摘要，不删除计量与恢复证据。未来恢复仅在这些证据完整匹配时认可其终态；没有退役证明的孤立记录仍拒绝，非零目录版本也不能因记录丢失就冒充空节点。

## 停站备份门禁（v0.2.4）

手动与定时整站备份共用严格门禁：同一数据库写事务内，核对完整受管链路的 v2 / keep_last 能力、持久化与最新命令 ACK、当前策略/代次及 90 秒内的管理和运行报告，再写入 `backup_pause` 冻结记录。90 秒是计划停站前的证据新鲜度要求，不是节点离线停用倒计时，也不是业务连通性保证。

存在 v1 / 混合链、未确认配置或停止、孤立命令、恢复冲突、账务降级、未结束或结果未知的执行任务、进行中网页备份、损坏记录时，默认停站前拒绝。旧链路中断风险只能通过受限 root 运维流程逐项确认；即使完成该确认，也仅放宽“不支持离线保留”这一能力检查，其余门禁不变，不能通过环境变量、定时任务或超时绕过。公共安装菜单不提供该入口。没有受影响规则的空站仍可备份，但同样需要获取门禁。

所有 `Store.Update` 在数据库行锁内重新检查门禁，冻结涵盖新规则、任务领取、同步/账务、管理员本机改密及后台写入；HTTP API（包括 GET 支付回调和执行机轮询）暂回 503。Node v2 保留配置，补报数据等待恢复后的明确 ACK。网页备份在写文件或上传前登记 `backup_operations`，与获取停站门禁互斥；最终结果与活动标记清除同事务提交，防止检查后启动外部备份工作。

本机 `msboost-restore backup-pause begin/end/check/status` 仅 Linux root、现有 PostgreSQL，不初始化数据库、不启动应用任务。随机解锁凭据仅存在独立 0700 暂存目录内的 0600 文件，经 stdin 传入，数据库只留摘要，结果和日志不输出凭据。`check/status` 只读检查不等于停站许可。`begin` 提交后才允许停止原有控制面容器，冻结贯穿全部导出，`end` 确认后才恢复原容器并检查健康；不操作 Agent/GOST 或 Docker daemon。

门禁及外部备份活动标记没有自动过期。整站门禁结果不明用原凭据幂等释放；释放失败则保留私有工作目录、阻止恢复并打印本机处理命令。进程被强杀时必须先核对仍在执行的备份，不能仅因时间过去就清标记。标准恢复器清除快照携带的本机门禁/活动标记，但继续执行 `recovery_required` 隔离；原始 SQL dump 仅作核查，不可直接重放作为安全恢复捷径。

新网页备份在同一准入事务内获取原数据目录的持久文件锁，活动记录绑定随机身份、设备号和 inode，持锁直至最终结果与标记清除提交；上传 panic 不标记成功、不清标记。原卷被持锁的活动不能被核销。受限原卷核销只允许在原受管服务器的 root 真终端进行，固定本机 Docker、原 server 镜像/挂载和实际数据库；以只读数据卷独占原锁后，在同一数据库事务核对精确 ID 与原始记录指纹，仅转存为 `interrupted_unknown` 审计。结果输出失败可对精确记录幂等核对，不删除文件、不宣称上传成功，不解除整站门禁或中转恢复隔离。公共安装菜单不提供核销入口。

旧无锁记录、原锁缺失/损坏/替换、多个活动或身份变化一律保留现场拒绝，不能用复制的锁文件或超时替代原锁证据。该受限流程只支持原官方单机 Compose 部署，不支持跨主机共享数据库或自定义挂载核销。Windows 锁回归为进程内模拟；临时 Debian 12 和独立 Linux CI 已通过真实跨进程锁、原卷只读容器权限和 PostgreSQL 并发核销。这些分项结果不等于所有部署环境的完整现场验收。

## 实测范围与剩余发布边界

- 真实 GOST 单跳与多跳 TCP/TLS 的 5/30 分钟受控管理故障矩阵已通过，原连接拨号一次且零重连。独立真实后端连续关监听 5 分钟、30 分 0.52 秒也已通过，停站新连接成功，恢复原命令与新鲜 ACK；这些专项结果达到 30 分钟耐久标准，但仍须核对实际部署制品和环境。
- 真实 Linux/Debian 12 文件权限、跨进程锁及进程退出已通过；有界1MiB tmpfs的真实ENOSPC/EROFS与原GOST保持已通过，但宿主级资源竞争、长期压力及客户服务迁移全链仍未验收，本机 Go TCP helper 不能替代这些环境。
- 停站备份门禁、管理员维护、并发恢复及原卷核销的真实 PostgreSQL / Compose 分项已通过；这些结果不能单独证明完整停站备份不中断。
- 真实手动/定时备份、导出/打包/SFTP上传失败恢复与同一GOST TCP的五阶段联合验收已通过；包含完整PG/加密状态/原卷归档校验和新鲜ACK，不代替全新控制面接管或多机全矩阵。
- 受信灾难恢复接管、证书维护、逐链路启用/回滚流程的真实环境验收；代码及故障回归已实现，见 [操作手册](relay-recovery.md)。记录达到硬上限后拒绝新增，不自动清除墓碑；长期容量需维护和退役原身份，不能承诺无限保存。
- 异常网页备份受保护核销的真实 Linux / Compose 已通过；旧链路手动维护备份的真实终端完整流程仍需验收，两者不混为同一用例。

v0.2.4 的历史安装行为是显式选择 keep_last；当前新装默认 keep_last。默认值变化不会消除以上边界，也不会自动升级、重启或迁移现有客户节点。不能把受控耐久测试宣称为生产全场景“离线不断流”保证。
