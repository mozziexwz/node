# 一键整站灾难备份与恢复

适用：v0.2.3 起，Debian 12，官方一键安装管理的 `/opt/msboost`。不能把本页新命令用于旧 v0.2.2 二进制。与[网页安全恢复和独立新库恢复](backup-recovery.md)并存。

## 备份和计划

升级到含此功能的正式版本后，运行 `msboost` 菜单，或：

```bash
msboost disaster-config
msboost disaster-backup
```

配置向导设置本地目录（默认 `/root/msboost-backup`）、保留天数（默认 30）、每日时间（默认 02:30，按 VPS 本地时区），可选远程公网 IP、SSH 端口、用户名（默认 root）、目标目录与密码。密码从不回显的终端读入；本机 `/opt/msboost/disaster.json` 为 0600，仅 root 可读。不要把该文件公开发送。重新运行此向导会重设计划；选择远端时需重新输入密码，密码留空不会沿用旧凭据；远程 IP 留空则改为仅本机备份。

整站远程 SSH 使用 Ed25519 主机密钥，指纹必须在目标服务器可信控制台核对，例如运行 `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`，不要仅因网络扫描看到了某个指纹就信任它。只有 ECDSA/RSA 的远端需管理员先配置 Ed25519；安装器不修改远端 sshd。远端专用目录须由 SSH 登录用户所有、权限为 0700；所有上级目录须由 root 或该用户所有，且不可被组或其他用户写入。已有目录不安全时拒绝上传，不自动放宽权限或修改归属。非 root 用户应选择其可管理的专用目录，不能直接沿用 `/root/msboost-backup`。

只有配置最后明确输入 `YES`，才启用 systemd 每日自动备份。停用：

```bash
msboost disaster-disable
systemctl status msboost-disaster-backup.timer
journalctl -u msboost-disaster-backup.service --since today
```

备份短暂停止原本正在运行的控制面网页与后台写入，数据库保持运行，导出后恢复原服务并等待健康检查。客户独立 VPS 不在备份/恢复操作范围内。已发布旧版的 v1 中转仍可能因短租约暂停；新版 v2 必须通过下述逐段门禁，不把管理失联当作停止指令。不要把备份计划设在业务高峰，配置保留不代表任意资源竞争下都没有延迟抖动。

### v0.2.4 的 v2 停站门禁（不适用于 v0.2.3）

v0.2.4 已给普通手动和定时整站备份加入严格停站门禁。它检查每条受影响转发链的实际 v2 / keep_last 能力、最新配置与停止确认，并要求报告在 90 秒内；单凭版本字符串不通过。存在 v1 / 混合链、未知或待确认状态、账务降级、运行中或结果未知的任务、未核实结束的网页备份时，在停止任何服务前失败并输出原因。自动计划没有降级或强制选项；旧站不能仅更新此脚本便假定能继续执行原有停站计划，需要先完成链路迁移与验收。需要接受旧链路中断进行单次维护备份时，使用下述独立交互入口，不修改自动计划。

检查与持久冻结使用同一数据库事务，全部控制面写入和 API 暂停，避免检查后又创建规则或领取任务。冻结期间 v2 节点应保留原配置，流量补报等待恢复后的确认；这个设计不替代真实 GOST / 长连接验收。导出完成后先解除门禁，再启动原先暂停的容器。空站无受影响规则也要获取门禁。工具不支持新命令、检查失败或提交不明时，均不会获准停站。

随机门禁凭据写入本轮 root-only `/root/msboost-disaster-work.*/backup-pause.token`，不进入命令行、日志或备份包。失败清理只使用原文件；解除失败则保留目录，不自动重启控制面。日志会打印核对后可用的本机解除命令与原服务集合。不要公开 token 内容，不要生成替代 token，不要在备份仍运行时手工解除。没有超时自动解锁；SIGKILL、宿主机断电或数据库错误后必须核对现场。网页备份残留 `backup_operations` 也不自动过期；仅符合原锁证据的新版记录可以用下述受保护入口核销，不能直接删除记录冒充操作结束。

标准恢复器会去掉快照的本机门禁和活动标记，但保留中转恢复冻结与旧资源关联。`database.dump` 可能带有当时的冻结记录，且本就不包含完整恢复隔离步骤；只供离线核查，不直接重放以开放站点。更多边界见 [Relay v2 契约](relay-v2-contract.md)。

### 单次手动维护备份：明确接受旧链路中断

配套脚本与固定镜像均更新后，原 Linux / Debian 12 服务器的 root 可从菜单 14 或以下无参数命令进入：

```bash
msboost disaster-backup-maintenance
```

必须从真实 `/dev/tty` 逐次输入 `BACKUP_WITH_RELAY_INTERRUPTION`。管道、确认文件、无终端、错误确认、`--yes` / `--force` 等参数和 systemd 自动执行环境均不能进入此路径。这个确认表示接受本次控制面停机后，旧 v1 / 混合链的短租约到期导致游戏连接中断；恢复控制面后可能仍需客户端重连。它不是“无感备份”，也不升级、停机或重启客户节点。

风险确认只允许忽略 `offline_unsupported` 与 `offline_unconfirmed` 两类离线能力不足。节点、用户、线路关系不完整，旧协议标记混入 v2 命令证据，配置无效，陈旧或未确认的 v2 状态，账务异常，恢复冲突，执行中或结果未知的任务，以及任何网页备份活动仍然拒绝停站。未来新增的阻止原因默认不可绕过，不提供通用强制开关。

检查和冻结仍在同一数据库事务中完成；门禁记录本次 `maintenance` 模式和已接受的风险代码，并留下 root 审计。只有获得门禁后才停止原本运行的控制面容器；导出、释放原 token、恢复健康、失败保留材料的顺序与严格备份相同。模式不同不能复用同一 token 改写原请求，门禁没有自动过期；释放失败不会恢复控制面或假报备份完成。

`msboost disaster-backup` 和 systemd timer 始终使用严格路径，不读取环境变量切换维护模式。底层 `backup-pause begin-maintenance` 是本机 root 专用工具，通过容器 stdin 接收原 token 和精确风险确认；容器不持有操作员终端，因此真实 TTY 门禁由上述官方管理入口负责。不要把底层特权工具或自动生成的确认语句放入 timer / cron，也不要把此手动路径设为日常备份计划。

### 异常网页备份核销（v0.2.4）

此入口只处理**网页备份进程异常退出后遗留的活动记录**，不是整站灾备门禁的解锁入口，也不是中转灾难恢复接管。安装脚本和已固定镜像必须都包含配套实现；仅下载新脚本不能让旧镜像支持该功能。v0.2.3 不具备此入口，须完成 v0.2.4 网站升级后使用。

在原 Debian 12 官方单机 Compose 部署的 root 交互终端，菜单 13 或以下无参数命令先做只读核对：

```bash
msboost backup-reconcile
```

入口核对原 server 的固定镜像、实际 `/app/data` 数据卷和数据库配置，以及本机唯一且健康的数据库容器。辅助程序固定连接本机 Docker，不拉取镜像、不启动或停止原服务；原数据卷只读挂载，使用最小读取权限检查锁。自定义挂载、远程 Docker、跨主机共享 PostgreSQL 或替代卷不在支持范围。

新网页备份从登记到最终结果提交持续持有 `app_data` 内的 `backup-activity.lock` 排他锁。锁文件永久保留，活动记录绑定其随机身份、设备号与 inode；不是按文件是否存在判断进程是否运行。核对时若仍被占用、锁丢失/损坏/被替换、记录属于旧无锁格式、存在多条活动或整站门禁尚未解除，命令会拒绝，不出现可绕过检查的强制选项。不要删除、复制替换、改权限或重建锁文件来使检查通过；新锁首次落盘失败也需保留现场，不能自动修复原证据。

仅证据符合时，终端显示精确活动 ID 和开始时间，要求输入对应的 `RECONCILE_BACKUP <活动ID>`。用户确认不是结束证明：辅助程序会重新获取原锁，并在数据库事务内再次验证当前原始记录的指纹，避免核对与确认之间记录变化。通过后将该活动移入 `backup_operation_reconciliations`，状态为 `interrupted_unknown` 并留下审计；不修改已有备份结果、不删除本机或远端文件，不影响财务、维护开关或中转恢复冻结。新网页备份候选文件使用 `<活动ID>.msb`，仅找到文件不代表完整、上传成功或可恢复，仍需独立校验。

提交或结果输出不明时保留日志，重新运行先只读核对；底层对同一 ID / 指纹提供幂等核对，不会把后来的另一项活动当作原记录。如果已没有待核对活动，命令只报告当前无活动，不会补报某个备份成功。原锁丢失或旧记录无法证明结束时继续保守拒绝，需保留数据库、文件和进程现场单独排查，没有超时自动核销。

此实现已通过本地 Go 和 Shell 模拟回归；Windows 测试使用模拟锁，Linux 跨进程测试仅完成交叉编译。真实 Debian 12 `flock`、只读卷与容器权限、PostgreSQL 并发行为仍待隔离环境验收，不能将本节当成生产验收报告。

### 备份内容与保留策略

快照包含：

- `state.msb`：可由独立恢复器导入的完整加密业务状态；导出事务只读，不启动后台任务。
- `database.dump`：PostgreSQL 原始自定义格式导出，供离线核查，不会自动重放进业务库。
- `site.env`：原域名、管理员、主密钥、数据库密码与固定镜像摘要。
- `deployment.tar`：部署文件和已有整站计划配置，只留作参考，不执行包内脚本或 Compose。
- `app_data.tar`、`caddy_data.tar`、`caddy_config.tar`：应用文件、历史业务备份、证书及代理数据。
- `manifest.json`：版本、时间与逐文件大小/SHA256。

单个整站包上限 64 GiB，业务快照及其解密状态仍受现有 100 MiB 上限限制；超限会失败并保留私有工作目录，不生成被当作成功的最终包。数据卷不接受链接、设备、特权文件或危险归档路径。GitHub/GHCR 不可用时，已安装站点从本机已固定镜像提取工具，正常备份不依赖再次下载程序。

归档权限检查仅对目录允许 sticky 位 `01000`，保留 Caddy 官方 `/data/caddy`、`/config/caddy` 的标准 `01777` 权限；它是目录内的删除保护位，不是提权位。[Caddy 官方镜像定义](https://raw.githubusercontent.com/caddyserver/caddy-docker/master/2.11/alpine/Dockerfile)明确设置了这两处权限。普通文件仍拒绝 sticky，所有条目仍拒绝 setuid、setgid 和其他非普通权限位；链接、设备、稀疏扩展、重复或危险路径的限制不变。不要为使备份通过而删除 sticky 位或修改真实数据卷权限。

本机保留策略只清理专用目录里命名和内容均验证通过的本站整站包，按天数保留，始终至少保留两份有效副本。损坏文件、临时文件和不相关文件不用于凑够份数。异地上传失败时本机有效副本保留，不执行后续清理。

远端默认不自动删除。配置时另外明确输入 `YES` 才按相同保留天数清理远端；该操作仅在新包上传和回读成功后执行。为确保至少留两份真正有效的副本，会把远端所有受管候选包逐份下载到本机私有临时目录校验，消耗回传流量和临时磁盘空间。任一候选下载、校验或连接失败则不开始清理；不删除远端目录、不跟随符号链接、不处理其他文件。上传失败遗留的私有 `.partial` 文件不参与自动清理，需管理员单独检查。

远端候选超过 500 份时停止自动清理，需人工分批整理；每个候选在删除前再次完整校验，避免只按秒级时间戳判断内容未变。本次上传和清理共用有上限的连接，网络过慢或超时会报告失败，已成功保存的本机包不删除。

普通卸载会停用整站计划，保留配置和备份；修复不自行重新启用计划。彻底清理删除本站计划文件、`/opt/msboost` 与本站数据卷，但不删除独立的 `/root/msboost-backup`、其他本机备份目录或远程备份。请按独立备份的敏感程度自行保管和清理。

## 全新 VPS 一键恢复

先停止旧站点并保留旧磁盘，不要让新旧控制面同时运行。准备**同架构 Debian 12 全新目标**、原域名 DNS/防火墙和可信的整站 `.tar.gz` 包。将包安全上传到新 VPS，保持仅 root 可读；**不要先执行普通安装**，它创建的 `/opt/msboost` 和数据卷会使整站恢复拒绝继续。已有站点或损坏库应使用[独立新数据库恢复](backup-recovery.md)，不要为了满足“全新目标”而清理原数据。

使用与备份 `MSBOOST_VERSION` 一致、经核验的正式安装入口。以下以 v0.2.3 备份为例；先把版本和包路径改成自己的实际值，再在新 VPS 的 root 终端执行：

```bash
backup_version=v0.2.3
apt-get update && apt-get install -y curl ca-certificates
curl -fsSL --proto '=https' --tlsv1.2 "https://raw.githubusercontent.com/mozziexwz/node/${backup_version}/install.sh" -o /root/msboost-install.sh
bash /root/msboost-install.sh disaster-restore --archive /root/msboost-backup/你的整站备份.tar.gz --version "$backup_version"
```

安装入口会下载指定版本的部署包和恢复工具，并用该 Release 的 `SHA256SUMS` 校验。不要为了恢复而升级到另一个版本。也可从新安装入口菜单选择“一键灾难恢复”，但必须使用与备份同版本的入口；新 VPS 尚无 `msboost` 命令。

恢复校验整站包、检查全新目录/卷/网络/端口，要求输入 `RESTORE_NEW_MSBOOST` 才继续。`/opt/msboost` 或同名卷/网络已有内容时拒绝接管。镜像从官方固定摘要或同版本 Release 备用归档取得，并核对原 imageID；自构建镜像、自定义 Compose/环境及跨架构迁移需要人工恢复。恢复保留原 `PUBLIC_URL` 和站点地址，不自动改域名或 IP：域名站点需将原域名解析到新 VPS；原先使用 HTTP IP 调试地址且新机 IP 不同的情况，需要人工审核地址迁移，不属于此一键恢复的地址变更功能。

恢复器使用原主密钥，只创建全新 `msboost_restore_...` 数据库，校验全部数据后再导入并读回；不会直接回放原 SQL dump。维护开启、支付/购买关闭、会话失效、Agent 令牌撤销、运行中任务中止而不重放。镜像恢复、后台业务与前台开放是不同阶段。

登录后核对用户、钱包账本、订单、权益、流量、文章与附件，与支付商核对备份时间之后的收款；重新关联 Agent 和必要规则，确认无误后手动解除维护并开启经营功能。原每日备份计划不会自动启用，核对远程目标后重新配置。

## 失败与中断

备份出错会尝试恢复原先运行的网页/后台服务。失败时会输出 root-only `/root/msboost-disaster-work.*` 工作目录；保留它和日志检查磁盘、文件权限与数据库健康。若重新启动也失败，立即用 `msboost status`、`msboost logs` 检查，不要先清理数据。

灾难导入成功之前保留 `/opt/msboost/.disaster-incomplete` 隔离标记。失败后 `repair` 和普通启动不会绕过它启动一个空站点。**不要盲目删除标记**：需确认新库完整导入、读回验证且保持维护，或者保留现场后在另一台全新 VPS 重新恢复。已恢复部分卷和新库不会自动删除，以便排查。

恢复数据已导入但 HTTPS/DNS 健康检查失败时，会保留新库和配置，按提示修正 DNS/端口后 `repair`。已经开放过营业后，不要再从旧备份覆盖或来回切换数据库，应先停写并对账。
